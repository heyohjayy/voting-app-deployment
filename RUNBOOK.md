# RUNBOOK

## 1. Overview

This runbook provides operational guidance for responding to security findings generated by the hardened CI/CD pipelines implemented in this project.

The pipelines incorporate automated security controls that execute before Docker images are published or deployed. These controls are classified as either **Gates** or **Signals**.

- **Gates** immediately stop the pipeline when a security issue that could compromise the application is detected.
- **Signals** report findings for developer review while allowing the pipeline to continue.

For this implementation, **TruffleHog** is configured as the project's only **Gate**.

Although **Dependency Audit** and **Trivy** are commonly implemented as Gates in production environments, they have intentionally been configured as **Signals** for this project because the Example Voting App contains known legacy vulnerabilities inherited from the upstream application. Blocking deployment on those findings would prevent the project from demonstrating the complete CI/CD workflow while providing little educational value.

This runbook describes how to respond whenever a Gate or Signal produces findings during pipeline execution.

# 2. Gate Failure Procedures

## 2.1 TruffleHog

### Purpose

TruffleHog scans the complete Git history for verified secrets such as API keys, access tokens, cloud credentials, and other sensitive information.

Within this project, TruffleHog is configured as a **Gate**. Any verified secret immediately terminates the pipeline before a Docker image can be published or deployed.

### Typical Causes

Examples include:

- GitHub Personal Access Tokens
- AWS Access Keys
- Azure credentials
- Google Cloud credentials
- Private keys
- Other verified secrets committed to the repository

### Response Procedure

1. Open the failed Jenkins pipeline.
2. Identify the TruffleHog stage.
3. Review the reported secret.
4. Locate the affected file within the repository.
5. Remove the exposed secret from the repository.
6. Replace the secret with an environment variable, Jenkins credential, or other secure credential management mechanism where appropriate.
7. Commit the corrected code.
8. Push the changes to GitHub.
9. Verify that the pipeline completes successfully.

### Important

Verified secrets must never be ignored or baselined. Any exposed credential should be considered compromised and should be revoked or rotated immediately after removal from the repository.

# 3. Signal Review Procedures

Signals report findings without preventing deployment. Every Signal should still be reviewed to determine whether corrective action or documented acceptance is appropriate.

## 3.1 GitLeaks

### Purpose

GitLeaks scans the complete Git history for potential hardcoded secrets using pattern matching and entropy detection.

Unlike TruffleHog, GitLeaks may report false positives. For this reason, GitLeaks is configured as a **Signal** within this project.

### Response Procedure

1. Review the GitLeaks findings in the Jenkins Console Output.
2. Determine whether the reported finding is a genuine secret or a false positive.
3. If the finding is a genuine credential, remove it from the repository immediately.
4. If the finding relates to a known upstream issue that cannot reasonably be corrected within the scope of this project, document it using the approved baseline process described later in this runbook.
5. Commit any required changes.
6. Re-run the pipeline and confirm that the findings have been reviewed.

## 3.2 Hadolint

### Purpose

Hadolint analyses Dockerfiles for security, reliability, and container best practice recommendations.

Within this project, Hadolint is configured as a **Signal** because many findings represent recommendations rather than issues that necessarily justify blocking deployment.

### Response Procedure

1. Review the reported Dockerfile findings.
2. Determine whether each recommendation improves security or maintainability.
3. Correct the Dockerfile where appropriate.
4. If a recommendation cannot reasonably be implemented, document the justification using the project's baseline process.
5. Re-run the pipeline to verify the updated Dockerfile.

## 3.3 Dependency Audit

### Purpose

Dependency Audit examines each service's application dependencies for known security vulnerabilities.

During this project:

- Vote uses **pip-audit**
- Worker uses **dotnet list package --vulnerable**
- Result uses **npm audit**

Although Dependency Audit commonly acts as a Gate in production environments, it has been configured as a **Signal** because the Example Voting App contains known legacy dependencies inherited from the upstream project.

Blocking deployment on these inherited vulnerabilities would prevent completion of the project while providing little practical benefit.

### Response Procedure

1. Review the reported vulnerable packages.
2. Determine whether the vulnerability originates from the project or from the upstream; in this case, the Example Voting App.
3. Update vulnerable dependencies where practical.
4. If the finding relates to an accepted upstream dependency, document it through the project's baseline process.
5. Continue monitoring for future dependency updates that resolve the reported vulnerability.

## 3.4 Semgrep

### Purpose

Semgrep performs Static Application Security Testing (SAST) by analysing the application source code for potential security weaknesses and insecure coding practices.

Semgrep is configured as a **Signal** because static analysis findings frequently require developer review before determining whether they represent genuine vulnerabilities.

### Response Procedure

1. Review the reported findings.
2. Determine whether the issue is a true positive or false positive.
3. Correct insecure code where appropriate.
4. If the finding is accepted for this project, document it using the approved baseline process.
5. Re-run the pipeline to confirm that the code changes have been validated.

## 3.5 Trivy

### Purpose

Trivy scans the Docker image produced during the pipeline for known operating system and application dependency vulnerabilities.

Although Trivy commonly operates as a Gate in production environments, it has been configured as a **Signal** for this project because the Example Voting App contains known legacy vulnerabilities inherited from the upstream application.

Blocking deployment on these inherited findings would prevent successful completion of the CI/CD workflow while providing little additional value for this implementation.

### Response Procedure

1. Review the Trivy scan results.
2. Identify any reported Critical or High vulnerabilities.
3. Determine whether the findings originate from the application or from the upstream; in this case, the Example Voting App.
4. Update affected packages where practical.
5. If the findings relate to accepted upstream vulnerabilities, document them using the project's baseline process.
6. Continue monitoring future image updates for security improvements.

# 4. Baseline Management

## 4.1 What is a Baseline?

A baseline is a documented record of an accepted security finding that is known to exist but will not be treated as a pipeline failure.

Baselines allow the security scanners to continue inspecting the complete repository while distinguishing known, accepted findings from newly introduced issues.

Within this project, baselines are used only where necessary to accommodate known findings inherited from the upstream Example Voting App. They are **not** used to suppress newly introduced vulnerabilities or to avoid correcting security issues.

Examples of baseline files include:

- `security/baselines/gitleaks-baseline.json`
- `.trivyignore`
- `.semgrepignore`
- `hadolint.yaml`

Each baseline entry should clearly document why the finding has been accepted and when it must be reviewed.

## 4.2 When is a Baseline Acceptable?

A finding may be baselined only when all of the following conditions are met:

- The finding originates from the upstream Example Voting App or another accepted third-party dependency.
- Correcting the finding is outside the scope of this project.
- The finding has been reviewed and determined not to prevent the project objectives from being demonstrated.
- The finding is documented with a written justification.
- A review date has been assigned.

Baselines exist to acknowledge known findings, not to hide them.

## 4.3 When Must a Finding NOT Be Baselined?

A finding must **not** be baselined if:

- It exposes a verified secret or credential.
- It has been introduced during development of this project.
- It can reasonably be corrected without affecting the objectives of the project.
- It represents a newly introduced security issue that has not previously been reviewed.

Verified secrets detected by TruffleHog must never be accepted through a baseline. They must be removed from the repository immediately, and any exposed credentials should be revoked or rotated.

## 4.4 How to Baseline Legitimately

Follow the steps below when creating or updating a baseline.

1. Review the reported finding.
2. Confirm that the finding originates from the upstream Example Voting App or another accepted third-party dependency.
3. Confirm that correcting the finding is outside the scope of this project.
4. Create or update the appropriate baseline file.
5. Record the reason for accepting the finding.
6. Record the date the baseline was created.
7. Assign a review date.
8. Commit the updated baseline file to the repository.
9. Re-run the pipeline to confirm that only the accepted finding has been baselined and that no new findings have been unintentionally suppressed.

A baseline should only acknowledge known and accepted findings. It must never be used to suppress newly introduced vulnerabilities or verified secrets.

# 5. Exception Process

## 5.1 When an Exception May Be Requested

A security exception may be requested when a reported finding cannot reasonably be corrected within the scope of the project but also does not prevent the intended objectives from being achieved.

Examples include:

- Known vulnerabilities inherited from the upstream Example Voting App.
- Findings originating from third-party dependencies that are outside the project's control.
- Security recommendations that cannot be implemented without fundamentally changing the upstream application.

Security exceptions should be used sparingly and only when there is a documented justification.

## 5.2 Required Information

Every exception request should include:

- The affected security tool.
- The affected file, dependency, or Docker image.
- A description of the finding.
- The reason the finding cannot currently be corrected.
- The associated baseline entry, where applicable.
- A proposed review date.

## 5.3 Approval

Before an exception is accepted, the finding should be reviewed to confirm that:

- The reported issue has been investigated.
- The justification is appropriate.
- Correcting the finding is genuinely outside the scope of the project.
- The exception has been documented.

## 5.4 Expiration

Security exceptions should not be considered permanent.

Each approved exception should include a review date so that the finding can be reassessed following future dependency updates, upstream changes, or project enhancements.

## 5.5 How to Request an Exception

Follow the steps below when requesting a security exception.

1. Review the reported finding.
2. Confirm that the finding cannot reasonably be corrected within the scope of the project.
3. Document the affected security tool, file, dependency, or Docker image.
4. Record a clear justification explaining why the finding cannot currently be resolved.
5. Record a proposed review date.
6. Submit the exception for review.
7. If approved, document the exception and update the appropriate baseline where applicable.
8. Re-run the pipeline to confirm that the documented exception behaves as expected without suppressing unrelated findings.

Security exceptions should be temporary. They should be reviewed periodically and removed once the underlying issue has been resolved.
